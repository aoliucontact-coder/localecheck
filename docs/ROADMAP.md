# LocaleCheck 产品发展路线图

> 制定日期：2026-09-07  
> 规划周期：8 周  
> 文档性质：未来待实现目标，不代表已完成成果  
> 使用方式：每周更新实际结果；所有对外表述以仓库中可复核的代码、测试、数据和用户证据为准。

## 1. 当前状态

LocaleCheck 面向已有中文产品、准备发布或维护英文版本的中国独立开发者和小型产品团队，首个场景是中英产品界面文案审校。

项目已经形成较清楚的产品定位、第一版范围、风险边界、用户研究方案和评测框架。应用源码与原始提交历史已经恢复到仓库；CSV 导入、规则检查、人工确认、安全导出和 AI 服务端边界均有可运行实现。当前自动门禁覆盖 40 项测试、42 条合成规则开发案例、类型检查、静态检查、格式检查和生产构建。

上述评测案例全部是开发用合成数据，只能证明实现与当前用例一致，不能证明真实场景效果。当前第一优先级已从“恢复工程”转为“获取用户与真实材料证据”；外部 CI、独立新环境复现、真实模型调用和完整浏览器端到端测试仍待完成。

## 2. 八周总体目标

在八周内完成一个公开可运行、可复现评测、经过目标用户验证的中英产品文案审校 MVP，并用真实数据说明 LocaleCheck 相比直接使用通用聊天模型在哪些问题上更可靠或更高效。

周期结束时应形成以下五类成果：

1. **可审计仓库**：完整源码、清晰提交历史、安装说明、自动测试和安全配置说明。
2. **可运行产品**：公开演示环境，能够完成导入、审校、确认和导出的完整流程。
3. **可复现评测**：80—100 条标注案例、独立测试集、评测脚本和结果报告。
4. **用户证据**：至少 5 次目标用户访谈、至少 3 次真实材料试用和两轮有记录的产品迭代。
5. **求职材料**：演示视频、案例研究、架构图、迭代记录和有数据依据的简历描述。

## 3. 八周实施计划

### 第 1 周：恢复工程基线

#### 目标

把文档中记载的产品恢复为任何人都能在仓库中复核和运行的工程。

#### 任务

- 找回并展开完整应用源码，以普通文件目录提交到仓库。
- 删除或排除压缩源码、构建产物、缓存和密钥。
- 建立清楚的源码、测试、文档和示例数据目录。
- 补充安装、启动、测试、构建和环境变量说明。
- 建立持续集成，至少运行类型检查、自动测试和生产构建。
- 逐项重新验证背景文档中记录的已有功能。

#### 验收标准

- 新环境按照 README 可在 15 分钟内启动项目。
- 类型检查、自动测试和生产构建全部通过。
- 至少恢复并复核背景文档记载的 8 项核心测试。
- 仓库不包含真实 API 密钥、无说明的大型文件或压缩源码包。
- CSV 导入、检查、人工确认和导出流程能够完整运行一次。

未满足以上标准前，不开始扩展 AI 功能。

### 第 2 周：验证真实用户问题

#### 目标

确认目标用户是否确实需要批量审校已有英文产品文案，并确定最值得优先解决的问题。

#### 样本要求

- 访谈 5 位目标用户。
- 至少 3 位受访者在最近三个月内处理过英文产品文案。
- 每次访谈 20—30 分钟。
- 尽量收集至少 3 份脱敏真实材料；无法提供文件时，记录具体错误实例。
- 先询问既有流程和真实经历，再展示产品，避免功能引导。

#### 必须记录

- 最近一次英文产品上线或更新流程；
- 使用的工具、文件格式和交接方式；
- 翻译和最终审核分别由谁完成；
- 最近发生的具体错误及其影响；
- 每批文案数量和检查耗时；
- 最难发现的错误类型；
- 遇到语境不足时的处理方式；
- 对上传文本和调用模型的隐私顾虑；
- 是否愿意在下一次真实任务中试用 LocaleCheck。

#### 阶段决策门槛

- 至少 3/5 用户独立提到同一种高频或高风险问题。
- 至少 2/5 用户愿意提供材料或参与下一轮试用。
- 如果“批量审校已有译文”不是主要痛点，应在本周调整定位，而不是继续按原假设扩展功能。

### 第 3 周：建立规则评测基线

#### 目标

先证明确定性规则可靠，再评测模型判断。

#### 数据集计划

建立 100 条案例，建议分布如下：

| 案例类型 | 数量 |
| --- | ---: |
| 正确译文 | 25 |
| 数字错误 | 12 |
| 占位符错误 | 15 |
| 空译或漏译 | 10 |
| 术语不一致 | 15 |
| 明显语义错误 | 10 |
| 语境不足 | 8 |
| 仅属可选润色 | 5 |

至少争取 30 条来自脱敏真实材料。无法取得真实材料时，必须明确标记合成数据，不能与真实数据合并宣传。

#### 数据管理要求

- 70 条用于开发和调试，30 条作为冻结测试集。
- 每条标注预期问题类型、严重程度、判断依据和可接受修订。
- 冻结测试集在最终评测前不得用于调整规则或提示词。
- 为 CSV 解析、公式注入、编码、引号、换行和特殊字符增加边界案例。

#### 规则目标

- 数字、占位符和空译文三类问题召回率达到 100%。
- 术语规则精确率不低于 95%。
- 正确译文上的规则误报不超过每 100 条 3 个。
- 非法 CSV 必须全部被拒绝，并且不得覆盖当前有效数据。

### 第 4 周：接入真实 AI 审校

#### 目标

实现可解释、可追踪、可安全降级的模型审校。

#### 输出结构

每条 AI 结果至少包含：

- `issueType`：问题类别；
- `severity`：严重程度；
- `reason`：判断理由；
- `evidence`：对应原文或上下文依据；
- `suggestion`：建议译文；
- `needsContext`：是否因信息不足无法判断；
- `model`：模型名称或版本；
- `promptVersion`：提示词版本。

#### 产品约束

- 模型调用经过服务端代理，密钥只存在于服务端环境变量。
- 导入文本始终按不可信数据处理，防止文本内容被当作系统指令。
- 模型超时、限流或格式错误时不得破坏当前编辑状态。
- AI 结果与规则结果在界面中明确区分。
- 信息不足时允许返回“无法判断”。
- AI 建议未经人工确认不得写入最终导出结果。

#### 验收标准

- 连续运行 30 条样例时无未处理崩溃。
- 结构化输出解析成功率达到 98%。
- API 失败时保留原始数据、编辑内容和人工决定。
- 日志不包含密钥和不必要的完整敏感文案。
- 每次调用能够追踪模型、提示词版本、耗时和估算费用。

### 第 5 周：执行对照评测

#### 实验设计

使用同一个模型进行两组比较：

- **基线组**：直接把相同文案交给模型审校。
- **LocaleCheck 组**：结合产品背景、术语表、确定性规则、结构化输出和人工确认流程。

#### 记录指标

- 问题级精确率、召回率和 F1；
- 每 100 条正确文案产生的误报数；
- 严重问题漏检数；
- 建议直接采纳、编辑后采纳和拒绝的比例；
- 单条响应时间；
- 每 100 条文案的模型费用；
- 完成同一批审校任务的人工操作时间。

#### 目标值

以下数值是未来目标，不是已有结果：

- 严重问题召回率不低于 90%。
- 总体精确率不低于 80%。
- 正确译文误报不超过每 100 条 10 个。
- 数字和占位符问题漏检为 0。
- 相比直接模型基线，至少一个核心指标提升 15%，且其他核心指标没有明显恶化。

如果未达到目标，应如实记录失败原因、适用范围和模型能力边界，不得只选择有利案例展示。

### 第 6 周：真实任务试用与第一轮迭代

#### 目标

让至少 3 位目标用户使用自己的真实或脱敏材料完成完整任务。

#### 行为指标

- 首次成功导入率；
- 完成整批任务的比例；
- 每条文案平均处理时间；
- AI 建议直接接受、编辑后接受、拒绝和跳过的比例；
- 无法判断的比例；
- 导出成功率；
- 卡点、误解和需要指导的次数。

#### 可用性目标

- 3/3 用户无需远程代操作即可完成导入和导出。
- 核心任务完成率不低于 90%。
- 不发生数据丢失。
- 所有导入失败都显示可执行的修复说明。
- 至少 2/3 用户愿意在下一次类似任务中继续使用。

#### 迭代规则

本周优先修复：

1. 阻断完整流程的问题；
2. 导致错误判断或数据丢失的问题；
3. 至少两位用户共同遇到的问题。

### 第 7 周：第二轮迭代与发布准备

#### 任务

- 根据用户反馈完成第二轮迭代。
- 补全关键浏览器端到端流程测试。
- 桌面端保证完整操作，移动端至少保证内容可查看。
- 补充隐私说明和数据发送提示。
- 提供示例项目或一键加载示例。
- 完善错误恢复、加载、空状态和无模型配置状态。
- 部署无需项目所有者权限的公共演示。
- 发布 `v0.1.0`。

#### 发布门槛

- 持续集成全部通过。
- 关键流程至少在两个主流浏览器中验证。
- 100 条数据能够在产品限制内完成处理。
- 未配置 AI 时仍可完成规则检查、人工编辑和导出。
- 公开演示地址无需项目所有者权限。
- README 不包含无法由代码、数据或用户记录支持的成果表述。

### 第 8 周：作品集与项目复盘

- 产品流程图和技术架构图；

## 4. 统一产品开发流程

后续每项需求统一按以下流程推进：

```text
用户证据
  → 问题陈述
  → 成功指标
  → 最小方案
  → 验收用例
  → 实现与测试
  → 小范围试用
  → 数据复盘
  → 保留、调整或删除
```

每个功能开始开发前，必须写清：

- 对应哪个用户问题；
- 哪类用户在什么场景使用；
- 不解决会产生什么影响；
- 怎样算实现完成；
- 怎样验证功能确实有用。

每轮迭代结束后记录：

- 变更原因；
- 具体变更；
- 测试结果；
- 用户反馈或评测结果；
- 未解决限制；
- 下一步决策。

## 7. 主要风险与应对

### 7.1 仓库与成果脱节

**风险**：源码虽已恢复，但本地验证结果可能被误写成外部可复现或真实用户效果。
**应对**：继续区分本地门禁、外部 CI、独立环境、合成评测和真实用户证据；未完成项不得对外写成成果。

### 7.2 只证明能够开发功能，没有证明解决真实问题

**风险**：产品可能成为技术演示，而非有效的用户解决方案。  
**应对**：用户访谈早于大规模 AI 开发；功能优先级必须关联用户证据。

### 7.3 评测被调参过程污染

**风险**：反复查看测试案例并调整提示词，会高估真实泛化效果。  
**应对**：严格分开开发集和冻结测试集，版本化记录模型、提示词、参数、日期和费用。

### 7.4 模型输出被误认为确定事实

**风险**：语境不足或翻译存在多种合理表达时，模型可能产生错误但自信的建议。  
**应对**：保留“无法判断”，展示理由与来源，所有修改必须经人工确认。

### 7.5 项目范围不断扩大

**风险**：在核心价值尚未验证前投入多语言、账户、协作和支付，导致八周内无法形成闭环。  
**应对**：严格执行 P0/P1/P2；没有用户证据的新增功能默认不进入当前周期。

## 8. 当前立即行动

工程基线已经恢复并通过本地自动门禁。当前首要里程碑转为第二周用户验证：按 `docs/research/` 中的招募、访谈、证据编号和综合模板，完成 5 位目标用户访谈并争取 3 份脱敏真实材料。

工程侧仅处理阻断访谈试用、数据正确性或安全边界的问题。外部 CI 与独立新环境复现仍需单独留证；在取得真实用户证据和冻结测试集结果前，不把合成开发集指标表述为产品效果。
