# LocaleCheck：项目背景与当前共识

> 最后更新：2026-09-07  
> 用途：为后续 Codex 会话、产品设计、开发、评测和求职作品集整理提供统一背景。  
> 说明：本文区分已完成事实、产品决策和待验证假设，不把计划写成成果。

## 1. 发起者背景与目标

项目发起者是一名英语笔译专业研究生，希望寻找与 AI 高度相关的实习，目标岗位包括 AI 产品经理、AI 应用产品、Agent／工作流产品、语言类 AI 产品和模型评测相关岗位。计划约两个月后开始实习，希望通过一个公开、可运行、可解释的 GitHub 项目展示个人能力。

项目采用人机协作方式推进：发起者负责用户问题、语言质量标准、产品范围、功能优先级、验收、用户反馈和最终判断；Codex 协助完成需求整理、实现、测试、调试、文档和迭代。使用 Codex 编写代码是项目方法的一部分，但发起者需要能够解释产品逻辑、关键取舍、评测方法和已知限制。

这个项目需要展示的核心能力包括：

- 从真实业务场景中发现问题并定义目标用户；
- 把非标准翻译工作拆解成可执行、可评测的工作流；
- 理解大模型的能力边界，区分确定性规则、模型判断和人工判断；
- 通过需求文档、原型、数据、测试、用户反馈和迭代记录呈现完整产品过程；
- 如实说明哪些部分已经实现或验证，哪些仍是假设。

## 2. 方向选择

前期讨论过三个方向：翻译与工作流、通用 AI 工作流、金融信息或量化。最终选择 **出海内容用户 + 翻译审校工作流**，原因是：

1. 与英语笔译背景形成直接差异化，发起者能够判断模型输出的语言质量；
2. 两个月内较容易完成一个端到端产品，而不必同时补足复杂金融、统计和回测知识；
3. 容易找到独立开发者、小团队、翻译同学或出海内容人员进行试用；
4. 能自然展示需求拆解、Prompt／模型应用、效果评测、人工确认和迭代能力。

金融信息阅读或量化方向可作为未来扩展，不属于当前第一版范围。

## 3. 产品定位

产品名称：**LocaleCheck**。

目标用户：已有中文产品、准备发布或维护英文版本的中国独立开发者和小型产品团队。

首个场景：审查产品界面文案，包括按钮、菜单、提示语、错误信息、空状态、订阅页面和确认弹窗。

核心问题假设：机器翻译或大模型初译可能语法正确，但仍存在术语不一致、数字或占位符变化、漏译、操作含义错误、语境不匹配和不必要润色。小团队缺少结构化审校流程，需要快速发现高风险问题，同时保留最终人工决定权。

产品价值主张：

> 导入中文原文和已有英文译文，结合产品背景与术语表进行检查，展示问题依据与修改建议，由用户逐条确认后导出。

第一版核心流程：

```text
导入 CSV
  → 填写产品背景与术语表
  → 运行规则检查／AI 语义审校
  → 查看问题、依据和建议
  → 人工编辑并接受或拒绝
  → 导出确认后的译文
```

产品需要用实际效果回答一个关键问题：为什么用户不直接把文本交给通用聊天模型审校？LocaleCheck 预期通过可复用术语、批量处理、风险聚合、问题依据、人工确认、审校记录和可复核评测体现额外价值。

## 4. 第一版范围

第一版聚焦“审校已有译文”，而不是生成完整翻译项目。当前定义的输入格式为 UTF-8 CSV：

- 必填列：`id`、`source`、`target`；
- 可选列：`context`；
- `id` 必须非空且唯一；
- 首版最多处理 100 条文案；
- 导入错误需要给出明确原因，不能静默丢弃数据。

当前规则检查覆盖：

- 数字是否改变；
- 占位符名称和数量是否一致；
- 英文译文是否为空；
- 指定术语是否按照术语表使用。

每条审校结果应包含文案 ID、问题类别、来源、理由，以及在适用时提供的建议译文。用户可以编辑最终译文、确认修改或保留原译文。只有明确确认的修改才能进入导出文件。

第一版暂不包括：多语言、网页抓取、复杂文件格式、账号体系、团队权限、支付、云端项目存储和全自动发布。

## 5. 关键产品决策

### 5.1 规则检查与 AI 判断分开

数字、占位符、空译文和指定术语适合用确定性规则检查，结果较容易解释和复核。准确性、语气、界面语境和跨文化表达需要模型辅助或人工判断。

界面必须明确说明：“未发现规则问题”不代表译文语义正确。没有配置模型服务时，产品仍可完成规则检查、人工编辑和导出，不能生成虚假的 AI 结果。

### 5.2 人工决定是最终控制点

同一条文案可能同时出现多个问题。当前方案以整条文案作为最终确认单位，避免分别接受多个建议时相互覆盖。待处理或被拒绝的建议不会改写原译文。

### 5.3 信息不足时允许无法判断

缺少界面位置、操作结果或产品背景时，系统应该提示用户补充语境，而不是强行给出确定修改。可选风格调整也不能自动标成翻译错误。

### 5.4 数据与隐私

当前工作默认只保存在浏览器页面内，刷新页面会清空。用户需要主动导出结果。只有用户主动点击 AI 审校时，当前文案、背景和术语表才会发送到所配置的模型服务。

真实 API 密钥必须保存在服务端或托管平台的密钥管理中，不能进入前端、日志或 GitHub 仓库。导入文本应始终作为不可信数据处理，不能被当作系统指令执行。

### 5.5 导出用途分开

标准 CSV 保持字段内容，适合程序重新导入。表格安全版会为可能被电子表格当作公式执行的字段增加前缀，适合人工打开；界面需要说明安全版可能改变这些字段的文本形式。

## 7. 当前限制与未验证事项

以下内容不能表述为已经完成的成果：

- 真实 AI 语义审校尚未配置模型 API，也没有验证真实模型调用；
- 尚未采访 3—5 位目标用户；
- “术语、数字和语境审校是目标用户的高频痛点”仍是产品假设；
- 10 条示例均为项目自制的合成数据，不是真实用户材料；
- 尚未建立 80—100 条正式评测集；
- 尚未测量问题检出率、误报率、建议采纳率、审校耗时、模型费用或用户留存；
- 尚不能声称产品提高了准确率、节省了时间或获得了真实用户；
- 尚未完成完整的浏览器交互与视觉回归测试；
- 私人试用链接不适合作为最终公开求职演示链接。

## 8. 评测框架

计划建立约 80—100 条案例，覆盖：误译、漏译、术语、数字、占位符、语境不足、可选润色和正确译文。每条案例人工标注问题类别、依据、严重程度和可接受修订，不要求只有一种正确译法。

调试集和最终测试集必须分开，最终测试集不能用于调整提示词。每轮评测记录模型名称、提示词版本、配置、日期、输入数量和费用。

对比设计：

- 基线：使用相同模型直接审校相同文案；
- 产品方案：相同模型配合产品背景、术语表、确定性规则和人工确认流程。

需要记录的指标包括：

- 问题级精确率与召回率；
- 每 100 条正确文案产生的误报数；
- 建议采纳率；
- 漏检数量；
- 完成同一审校任务的时间；
- 响应时间和模型费用。

用户测试应使用难度相近的不同材料并交换使用顺序，减少重复阅读带来的熟悉效应。模型自评只能作为辅助，人工审校结果作为参考；条件允许时请第二位审校者复核争议案例。

## 9. 用户研究计划

首轮计划访谈 3—5 位已有中文产品、正在上线或维护英文版本的开发者。每次约 20 分钟，先询问最近一次真实工作经历，再展示产品，避免用产品功能引导答案。

需要了解：

- 当前从中文稿到英文上线的完整流程；
- 翻译与检查分别由谁完成；
- 使用的工具、文件格式和术语管理方式；
- 最近发生过的具体错误及其影响；
- 最费时间或最容易遗漏的步骤；
- 遇到语境不足时如何处理；
- 用户实际操作 LocaleCheck 时卡住的位置；
- 哪些提示真正有帮助，哪些属于误报；
- 产品进入现有工作流还缺少什么条件。

记录应区分用户原话、观察事实、研究者解释和下一步假设。礼貌性赞同不能当作需求验证。

## 10. 后续优先级

建议按以下顺序继续：

1. 将完整源码作为普通目录同步到当前 Git 仓库，建立清晰的提交历史；
2. 完成 3—5 位目标用户访谈，修正目标场景和功能优先级；
3. 建立第一批人工标注评测案例，先测规则检查的误报与漏检；
4. 选择并安全配置一个模型服务，验证真实 AI 语义审校；
5. 用相同模型完成“直接审校”和“LocaleCheck 工作流”的对照测试；
6. 根据用户反馈完成至少两次有记录的产品迭代；
7. 准备公开演示地址、短视频、项目复盘和适合简历的真实结果描述。

## 11. 后续 Codex 工作约束

后续 Codex 在本项目中工作时应遵守：

- 先阅读本文和当前需求文档，再更改产品范围；
- 优先完成小而完整、可以验收的用户流程；
- 所有模型输出必须标明来源并经过人工确认；
- 不把规则检查称为 AI 审校；
- 不把合成样例或内部测试称为真实用户证据；
- 不编造用户量、准确率、节省时间、采用率或商业成果；
- 真实密钥不得写入代码、浏览器或版本库；
- 新增功能应说明对应的用户问题和验收条件；
- 每次迭代记录变化原因、验证方式、结果和剩余限制。
